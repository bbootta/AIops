### 5.1 F-B03 (적합) — 통제가 이제 제출 실행을 덮습니다

`_structure()`가 라인명·라인코드의 날짜를 `<date>`로 정규화하고(정규식이
`YYYY-MM-DD` · `N월 N일` · `YYYYQn` 세 형태를 포괄), 그 결과 같아진 연속 키를
하나로 접습니다.

```
기준선          290서식  5,828키
제출본(06-30)   290서식  5,854키
→ 소실 0건 · 추가 0건        (11차에는 52건이 벌어져 통제를 돌릴 수 없었음)
```

11차 지적의 핵심은 "통제가 있는 것과 통제가 제출물을 덮는 것은 다르다"였고,

### 5.4 F-B01 (경부적합) — "공시한다"고 적었는데 공시되지 않았습니다

`_structure()`의 docstring:

> 한계 — 일별 계열 **안에서** 라인 하나가 사라지는 것은 잡지 못한다. …
> **요청서에 공시한다.**

요청 패키지의 도전 대상 가정 25건은 11차와 **집합이 완전히 동일**합니다 —
추가 0건 · 삭제 0건이고, `일별`·`접`·`구조 회귀`·`기준선`·`<date>` 어느
키워드로도 해당 문장이 검색되지 않습니다.

한계가 실재한다는 것도 실측했습니다:

```
기준선 5,828키   제출본 5,854키   → 26키 차이
통제는 집합 포함으로 판정 → 소실 0 · 추가 0 으로 통과
```

즉 일별 계열에서 라인이 사라져도 개수 차이가 흡수됩니다. **절충 자체는
합리적이고**(월별 영업일 수가 달라 개수 고정 불가) 판단에 동의합니다. 문제는
**그 한계를 아는 사람과 모르는 사람이 갈린다**는 것입니다 — docstring은 코드를
읽는 사람만 보고, 결재선과 3선은 요청서를 봅니다.

이 유형은 F-501 · F-603 · F-702 · F-801에 이은 반복이며, 이번에는 값이 아니라
**통제의 한계**가 문서와 어긋난 경우입니다.

### 5.5 F-B02 (경부적합) — "9건"이 실측 8건입니다

11차와 12차를 각각 별도 워크트리에서 같은 조건으로 빌드해 라인별 `citation`을
전수 대조했습니다. 바뀐 라인은 **17건**이고 두 부류입니다.

| 부류 | 건수 | 내용 |
|---|---:|---|
| **조항 오인용 정정** | **8** | 제1항 → 제2항 7건(BF202/4020 · BF405/1030·2130·2230·2330·2430·2530) · 제2항 → 제1항 1건(B2431/1030) |
| 조항 명시화 | 9 | "제29조 …" → "제29조 **제1항** …" (B2506/3000·3010·3020·3030·3040·3050·9900 · B2507/3000·9900) |

"9"는 **명시화 건수와 우연히 같습니다.** 오차의 원인은 셈법입니다 —
`test_citations` docstring이 "3선이 8건 표본에서 발견"(2건) 뒤에 "같은 유형이
**7건 더** 나왔다"를 더해 9로 계산했는데, 그 7건 안에 제가 찾은 2건
(BF202/4020 · BF405/1030)이 **이미 포함**돼 있습니다. 새로 찾은 것은 5건이고
다른 방향 1건(B2431)을 더해 8건입니다.

B2431/1030("최저적립 충족 여부", 제2항 → 제1항)의 방향에는 **동의합니다** —
충당금 ≥ 최저적립액 판정이므로 제1항이 맞습니다.

**정정의 실질은 모두 옳습니다.** 어긋난 것은 건수 주장뿐이고, 제출 서식이 아니라
코드 주석·커밋 메시지에 있습니다.
