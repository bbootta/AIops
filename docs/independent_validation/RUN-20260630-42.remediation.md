## F-207 (경부적합 · 선결) — 게이트 코드가 스스로 모순됐다

3선이 이번에 **판정 도구 자체**를 검증 대상에 넣었다. `ValidationResponse.passes`의
docstring은 "경부적합까지는 조건부 통과"라고 약속했으나 구현은
`verdict == "적합"`만 통과시켜, 약속한 조건부 경로가 **코드에 존재하지 않았다**.
`ValidationResponse(verdict="경부적합", findings=[]) → passes = False`.

우리 게이트로 3차 응답을 파싱한 결과가 정확히 그 상태다.

```
status : 부적합        reason : 판정 경부적합
중부적합 : (없음)      경부적합 : F-201 · F-202 · F-207
```

지적이 맞다. 판정 도구가 문서와 어긋나면 그 위의 모든 판정이 흔들린다.

**시정** — 세 번째 상태 `조건부`를 도입했다. docstring만 고쳐 "적합만 통과"로
맞추는 선택지도 있었으나, 그러면 문서 지적 수준의 경부적합 하나가 결재를 영구히
막아 게이트를 우회할 유인이 생긴다. 반대로 자동 통과시키면 사람의 판단이 사라진다.

| 상태 | 조건 | 결재 |
|---|---|---|
| `응답대기` | 응답 파일 없음 | 불가 |
| `부적합` | 중부적합 있음 · 재계산 불일치 · run_id/request_id 불일치 | 불가 |
| **`조건부`** | 경부적합 + 중부적합 0건 + 재계산 전건 일치 | **기록 있을 때만** |
| `적합` | 판정 적합 + 재계산 전건 일치 | 가능 |

`조건부`는 `require(ConditionalApproval(...))`로만 통과하며, 기록은
**잔여위험 · 후속조건 · 이행기한 · 배포 범위 · 결재자**를 모두 요구한다. 하나라도
비면 통과하지 않는다 — fail-closed는 유지된다. 기계가 이 기록을 대신 만들지
않는다.

재계산 불일치 검사를 판정 검사보다 **앞으로** 옮겼다. 어긋난 재계산은 어떤
판정과도 무관하게 부적합이어야 한다.

회귀 방지 테스트 7건을 추가했다 — 그중 `test_passes_docstring_matches_the_implementation`은
docstring이 약속한 경로가 실제로 존재하는지를 직접 검사한다.

| ×2 | 20.8조 | 0.089829 | 0.086762 |

| ×10 | 104조 | 0.068522 | 0.062471 |
| ×50 | 520조 | 0.064262 | **0.057613** |

×50에서 고정 발행자본은 총익스포저의 0.12%에 불과해 지적대로 반응성이 소멸한다.
현재 seed 42 기준 136.8bp의 반응성은 고정분 기여 52% 덕분이며, 자산이 몇 배만
커져도 유지되지 않는다.

**시정** — 두 가지를 했다. 합성 데이터에는 실제 자본 원장이 없으므로 원장을
기본 경로로 삼을 수는 없다. 대신,

1. **정책 명시** — 고정 발행자본은 자산 규모와 무관하게 유지한다는 규칙을
   `bis.py`에 못 박았다. 자산이 늘었다고 이 상수를 함께 키우면 자본이 다시
   규모의 함수가 되어 통제가 소멸한다. 수렴 실측치도 함께 남겼다.
2. **상시 감시 체크 신설** — `capital_source`(자체검증). 실제 원장을 주입하면
   PASS, 합성기를 쓰면 규모 비례분 비중을 계산해 50% 이상이면 **WARN**이다.

```
WARN | 합성 자본 사용 — CET1 1,094,368,959,484 중 규모 비례분(이익잉여금) 54.3%,
       고정 발행자본 기여 51.8% · 자산 대비 고정분 6.15%
       (희석될수록 레버리지 반응성이 소멸)
```

이 WARN은 `self_validation_warnings`를 통해 매 요청마다 3선과 결재선에
전달된다. 지표가 상수로 수렴하는 과정은 조용히 진행되므로, 비중을 매번 눈에
보이게 두는 것이 F-201·F-202의 공통 뿌리에 대한 상시 통제다.

## 3선 권고 반영

- **권고 4** (2·3차 연속 제기, "이 지표가 상수가 되는 입력 조합이 있는가"를
  자체검증 체크로) — 위 `capital_source`가 그 첫 구현이다. 자본이 규모의 함수가
  되는 정도를 매 실행 정량화한다.
- **권고 5** (`reverse_critical_severity`의 해석 폭) — 1차 0.9447 → 2차 0.8426 →
  3차 0.9822(진폭 0.14)로 자본 가정에 민감하다는 사실을 `KNOWN_ASSUMPTIONS`에
  넣어 결재선과 3선에 함께 전달한다.

## 자체검증 변화

WARN 4건 → **5건** (신설 `capital_source`). FAIL은 0건 유지.

## 시정 중 우리가 찾은 결함 — 요청 식별자가 내용 변경을 못 잡았다

3차 시정을 마치고 4차 요청을 만들었더니 `request_id`가 **IVR-573F73DBBF35 그대로**
나왔다. 공시 가정이 12건 → 15건, 자체검증 WARN이 4건 → 5건으로 바뀌었는데도
식별자가 같아, 그 변경을 본 적 없는 **3차 응답이 그대로 승인으로 통했다**
(게이트가 `조건부`를 반환했다).

원인은 `request_id = digest(run_id, headline_digest)` — headline **수치만**
지문화한 것이다. 이번 시정처럼 산출값이 하나도 안 바뀌는 시정(문서·통제·가정
공시)일수록 재검증이 필요한데, 게이트의 stale 방어가 정확히 그때 뚫린다.
F-207과 같은 종류의 결함이다 — 판정 도구 자체의 구멍이며, 3선이 게이트를 검증
대상에 넣지 않았다면 우리도 보지 못했을 것이다.

**시정** — 지문에 **3선에게 넘기는 것 전부**를 넣었다: `known_assumptions` ·
자체검증 요약 · FAIL 목록 · WARN 본문. 4차 요청은 `IVR-0DC4055ED5AF`로 바뀌었고
게이트는 3차 응답을 `부적합 — request_id 불일치`로 거절한다. 회귀 테스트
`test_request_id_changes_when_the_disclosed_content_changes`를 추가했다
(headline_digest는 그대로인데 식별자만 바뀌는지 확인).
